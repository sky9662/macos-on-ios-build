# Bounded ARM64 interpreter feasibility

This is an independently written experimental subset, not a replacement for the game's JIT or a complete AArch64 engine. It interprets immutable 32-bit A64 instruction words as data, with 31 64-bit guest registers (W writes zero-extend), a separate bounded little-endian guest data buffer, and a finite instruction budget. It accepts LSL-shifted 32/64-bit AND/ORR/EOR, immediate 32/64-bit ADD/SUB with or without NZCV flags, unsigned-offset 8/16/32/64-bit LDR/STR, 32/64-bit CBZ/CBNZ, B.cond (EQ through LE), MOVZ/MOVN/MOVK, B, and a synthetic RET boundary. All other opcodes, stack-pointer usage, indirect host calls and out-of-range guest accesses are rejected. No executable allocation or host memory alias is used. On error, discard the partial guest state.

Tests compare an independently authored full-adder fixture (all eight inputs) and memory-update loop (64 cases) against native ARM64 assembly on macOS; Linux runs the same expected outputs with sanitizers. iOS compile checks are not device runtime tests. No game content, disassembly, offsets or private records are committed. No third-party code is included. Reference design context: UTM SE and iSH ARM64, as discussed in jit/SOURCE-INTEGRATION.md.

The local audit suggests a candidate generated-code boundary; it does not establish ABI, all indirect paths, emitted opcode coverage, callbacks, complete flag semantics, stack, memory ownership, real-game performance or a lawful integration interface. This subset deliberately has none of those integrations. A broader engine should be evaluated against the real requirements before expanding this prototype. The existing packaging/JIT gate remains unchanged.

## Second feasibility round

First run 45979232930 passed both jobs (portable sanitizer tests and native ARM64 comparison / iOS compilation). Extend the isolated register model to 64-bit and all four unsigned-offset load/store widths. Test upper-half values, W zero-extension, 64-bit conditional branches, overflow and guest memory bounds. Add 1,024 wide-operation and 256 memory-width cases with independent native assembly comparisons, plus an optimized host-only timed loop comparison. The timing is a synthetic workload, not a device or game benchmark. No host pointers, executable allocations, callback integration or packaging gate changes. Instruction coverage is still deliberately small.

## Third feasibility round

Run 46121584053 passed both jobs; recorded synthetic CPU times 0.491416 s interpreted vs 0.013617 s native for 12,800,000 loop iterations. These are host-only measurements; not game or device speed. Add immediate flag-setting ADD/SUB (including CMP), integer NZCV and conditional branches EQ through LE, and MOVZ/MOVN/MOVK constants. Extend native comparison fixtures and arithmetic edge tests. The original no-SP, isolated-memory and no-host-callback constraints remain. No game ABI or code emission coverage has been established; do not claim this is a playable game.

## Fourth feasibility round: established simulator reference

Third round 46123752074 passed both existing CI jobs. Evaluate VIXL as a reference engine before further expanding our instruction subset. Upstream documentation: https://github.com/Linaro/vixl (historical mirror now redirects development to Arm GitLab); https://android.git.googlesource.com/platform/external/vixl/+/HEAD/doc/aarch64/getting-started-aarch64.md . The Linux-only test uses Ubuntu's signed libvixl-dev distribution package in the 5.1.0 series, records the exact package version and installed copyright, and fails on a different upstream series. No upstream code is copied or redistributed, and no library is packaged for iOS. This is a test dependency, not a pinned production runtime.

VIXL is designed to simulate generated A64 instructions; it is not an isolation boundary. The fixed trusted fixtures accept no external code, addresses or input files, invoke no host callbacks, and have a process timeout. Compare 2,056 shared cases against the bounded subset and test 128 MUL cases deliberately unsupported by our subset. This is a coverage feasibility check on Linux, not VIXL iOS compatibility, performance or a game integration. Before choosing a runtime, evaluate guest memory confinement, source provenance and licensing, iOS compilation and real workload needs. Retain the existing packer gate and no-host-pointer subset. No game-specific data is committed.
